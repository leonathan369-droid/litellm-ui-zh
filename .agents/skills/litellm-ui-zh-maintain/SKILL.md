# LiteLLM 汉化维护

路径均相对本仓库根目录。先读 [架构边界](../../../docs/architecture.md) 和 [维护 SOP](../../../docs/maintenance.md) 的任务相关部分；涉及版本验证再读 [兼容性记录](../../../docs/compatibility.md)。命令、核心页面和发布检查以 SOP 为单一入口，复用现有脚本，不另写一套安装器或浏览器测试框架。

## 选择本次范围

- **补翻译**：先取得目标版本真实 UI 文本及上下文，修改词典并构建；不自动升级 LiteLLM 或修改兼容版本记录。
- **运行时修复**：先复现误翻、漏翻、切换或初始化错误，最小修改 Overlay，并补覆盖真实失败路径的回归测试。
- **版本适配**：固定本次目标 LiteLLM 版本，执行隔离安装、服务、浏览器和页面检查；只按实际证据更新兼容状态。
- **同步汉化上游**：核对 Git remote 和差异，合入已授权范围；同步本身不等于兼容验收或发布。

用户只要求检查时保持只读。维护 skill、词条或本地验证不授权提交、推送、打 tag、发布 Release 或部署网关。已有同范围授权持续有效，不逐步骤重复询问。

## 上游与工作树

1. 检查当前分支、工作树和 remote。默认留在当前分支，保留他人修改；不自动建兼容分支、reset 或覆盖本地 fork 的修复。
2. 区分两个上游：Git `upstream` 指汉化 Overlay 的来源仓库；兼容性目标来自 `BerriAI/litellm` 官方发行版。使用实际 remote URL 和提交判断，不能把同步 Overlay 当成升级 LiteLLM。
3. 用户要求同步时，先 fetch 对应 remote 并比较提交和文件，再按授权范围合入；请求不含同步时不自动 merge。涉及合并冲突保留本地已验收行为，无法保持任务范围时只暂停冲突相关步骤。
4. 版本适配使用用户指定的精确版本；用户要求“最新”时实时核对官方发行状态和可安装包。SOP 中的 workflow 固定版本只是现有测试目标，不代表最新版本。RC/dev/nightly 可按明确请求试验，但不作为 stable 兼容发布目标。

## 翻译与运行时修改

1. 取得目标页面、标签/弹窗及切换前英文；静态扫描结果只是候选，新增词条必须核实真实原文和含义。不可进入的页面明确留作未验证，不臆造 UI 文案。
2. 普通固定文案优先改 `locales/zh-CN.json`，保留技术字段、模型名、项目名、日志、代码与业务内容。按架构中的 exact-match、表头上下文和跳过区域处理；不为覆盖率增加任意子串、通配或用户数据翻译。
3. 同一英文有不同含义时，先查现有上下文规则与真实 DOM。需要改运行时才改 `src/overlay.js`，并验证另一上下文及同名数据仍正确，不能只改全局词典让另一个位置误翻。
4. 动态文本/属性问题要覆盖 React 更新后的当前英文恢复、重复中英切换、加载骨架/hydration 和切换按钮生命周期；只补本次行为必要的测试。代码、输入值、普通数据单元格和独立 iframe 的保护边界不能被放宽。
5. 运行 SOP 的生成与基础检查，审阅词典、源文件和 `dist/litellm-zh.js` 差异。dist 必须由构建脚本生成；不得手工修补生成文件或仅为一次词条修改提升发布版本。

## 精确版本隔离验证

1. 用任务专属目录和独立 Python 环境安装目标版本，先核对实际版本与 packaged UI 位置；不升级用户已有 Python 环境或改写原版 UI。安装器 `--python` 必须指向目标环境，避免检查了另一个版本。
2. 按 SOP 选择 install/upgrade/check/diagnose：首次目标不存在时 install，只对本任务创建的测试目标做 upgrade。不要直接复制 README 中用户配置目录作为测试目标，不对未知目录执行 restore。记录任务创建的目录、端口与进程 PID，避开已有服务。
3. 比较实际服务返回的 Overlay 与构建产物哈希，确认目标页面引用正确。哈希一致只证明完整性；安装器显示的兼容状态来自已有记录，不能把它当作本次新版本已经验证的证据。读取来源版本和兼容状态的具体字段，不能只看 check 退出码；目标 Python 版本另用目标解释器核实，不从 diagnose 的安装器 Python 版本推定。
4. 用现有 `collect_strings.py` 扫描导出 HTML，逐项审核 unknown；版本适配时按 SOP 与静态 allowlist 比较，新增允许项需有明确保留理由。收集器返回成功不等于未知英文门禁通过；不能批量加入 allowlist 来消除失败，也不能把“无静态未知词”写成动态页面全覆盖。
5. 需要登录页面时使用独立数据库、虚构数据与本任务测试账号，复用 SOP 中现有路由检查入口。该脚本会输出页面正文预览及截图，不能直接用于生产；CI 的临时数据库初始化方式也不得指向生产/共享库。测试页面不提交会改业务配置的表单，不调用真实模型。
6. 逐页检查实际目标版本的路由与新增入口。既有脚本的固定路由、等待和 placeholder 断言需要对照目标版本；页面跳回 Home、权限不足或显示占位内容不能当作目标页面通过。
7. 浏览器自动化检查和人工截图目测分开报告；代码或 JS 测试通过不能代替布局检查。实时浏览器按用户显示约定保持全屏和 100% 缩放，截图用滚动或整页捕获；CI 的固定视口截图只算对应自动化证据。登录验证由用户完成时停在该流程，不索取密码/验证码。
8. 正常关闭本任务创建的浏览器并核实退出；共享浏览器只关本任务标签页。按已核实 PID 停止本任务服务，清理任务临时目录；正式兼容性证据按已确定位置保留并去敏，不提交 packaged UI、凭据、Cookie 或业务数据。

## 状态与交付

- 状态依据 [兼容性定义](../../../docs/compatibility.md#状态定义)。分别写明精确版本、系统、浏览器、页面/交互范围、代码提交或产物哈希、实际执行的检查与未验证项；不把 Ubuntu 结果扩展到 macOS，也不把本地结果写成 GitHub Actions 已通过。
- 局部文案或少数页面的验收只补对应记录，不自动更新 `latest_verified`、`latest_automated_verified` 或整个版本状态。版本适配完成后，按 SOP 同步 `compatibility/upstream.json` 与兼容文档；变更当前行为时同步架构/SOP，发布时再按授权更新版本说明。
- 对 `ai-gateway` 的交付只提供经过验证的源码提交、生成 JS 的 SHA256、许可文件和验证范围。需要同步到使用方时，先读该仓库规则及其 `ai-gateway-release` skill，沿用现有来源清单和打包流程；汉化仓库完成不代表网关已部署。
- 没有提交授权时报告工作树产物和哈希，不把旧 HEAD 标成新产物的来源。不能用本仓库 `install.py` 直接覆盖网关生产 UI，也不因翻译更新修改模型、Team、Key、报表或数据库。
- 实际请求范围完成、必要检查通过且评审无高/中问题即停止。最终说明修改、验证层次、未验证项、临时资源清理及 Git/发布状态。
